# 开发工作流与会话交接规范

## 分支策略

- `main`：唯一正式主线，只接收经过审查和验证的 PR。
- `feat/*`：功能开发分支；一个分支聚焦一个功能主题。
- `fix/*`：缺陷修复分支。
- `content/*`：文案、任务对话和内容数据草稿。
- `docs/*`：项目文档、规范和交接记录。
- 不在 main 上直接开展大规模功能开发；不对共享分支执行 force push 或历史重写。

## 开始工作前

1. 阅读 `README.md`、`docs/PROJECT_STATUS.md`、`docs/CHANGELOG.md`。
2. 检查当前分支、工作区状态、最近提交和远程分支。
3. 明确目标分支与基线 SHA。
4. 阅读目标文件及调用方/数据依赖；先给出影响范围，再改代码。
5. 保留用户已有未提交改动，不用 reset/clean/覆盖操作“清理现场”。

## 修改与提交

- 小步修改，一个提交表达一个清晰目的。
- 提交标题建议采用 `feat:`、`fix:`、`refactor:`、`art:`、`docs:`、`test:` 前缀。
- 提交前检查 diff，确认没有缓存、密钥、本地配置或无关文件。
- 任何涉及存档结构、资源 ID、场景路径或数据格式的修改，必须说明兼容策略。
- 每个有意义的提交都追加到 `CHANGELOG.md`，并同步更新 `PROJECT_STATUS.md` 中的状态和下一步。

## 验证分级

记录必须区分以下层级，不能互相替代：

1. 静态审查：读代码/比较 diff。
2. 导入检查：指定 Godot 版本完成项目资源导入。
3. 运行检查：主场景成功启动，观察日志和关键流程。
4. 功能回归：移动、战斗、地图切换、存档/读档及受影响系统。
5. Android 验证：导出并在目标设备安装运行。

没有执行的步骤标记“未验证”。CI 通过也不能自动代替设备实测。

## 会话交接

每次会话结束前：
- 更新 `docs/PROJECT_STATUS.md` 的已完成事项、当前分支/提交和下一步。
- 在 `docs/CHANGELOG.md` 记录本次提交及测试结果。
- 写清楚尚未解决的问题、复现步骤和相关文件路径。
- 不写“完成”除非对应验证已实际执行。

## 设计决策与竞品对标原则

当开发过程中遇到玩法、交互、地图结构、系统流程或技术方案不明确时，**优先参考成熟同类产品，不凭空停留在讨论，也不把本可自行完成的设计决策反复交还给用户**。

执行顺序：

1. **明确对标对象**：优先使用项目已确定的参考产品与品类标杆；地图与探索系统当前以《百炼英雄》为主要对标对象。
2. **研究具体机制**：拆解其世界地图/区域地图层级、区域连接与解锁、传送点、探索揭雾、资源与怪物分布、营地/Boss 节点、地图切换和进度保存等实际逻辑；不只参考截图或美术风格。
3. **结合本项目落地**：保留适合本项目的成熟机制，按现有 Godot 架构、竖屏单机体验和原创美术素材进行实现；不照搬受版权保护的素材、文案或专有表达。
4. **先验证再扩展**：先完成最小可玩的闭环，补充自动化测试与必要的设备验收，再扩展更多地图或系统。
5. **记录依据与差异**：在功能设计/开发记录中写明对标对象、参考机制、本项目采用方式、刻意不采用的部分及验证结果。
6. **遇到阻碍主动处理**：先查仓库文档、现有代码、测试和竞品资料；能合理判断的直接推进。只有涉及用户偏好、重大范围变化、付费/账号或不可逆操作时才向用户确认。

地图开发的默认目标体验：世界地图发现区域 → 进入区域地图 → 在场景中自由探索并揭开迷雾 → 发现怪物、资源、营地、Boss 与道路/传送点 → 达成条件解锁新区域或传送路线 → 保存各区域探索与进度。该流程是设计目标，具体实现状态必须以代码和测试为准，不得把目标描述成已完成事实。
