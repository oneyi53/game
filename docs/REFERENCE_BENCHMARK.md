# 《百炼英雄》对标拆解与验收基线

日期：2026-11-05  
参考对象：手游《百炼英雄》（TapTap 官方页面、官方公告、玩家实机截图与公开录屏）

> 本文记录可从公开实机截图、视频和游戏说明核实的设计事实，并将其转化为本项目的实现要求。不是照搬素材；美术资源继续使用项目原创资产。

## 0. 产品定位与双阶段验收策略（项目最高优先级）

**产品目标：先达到《百炼英雄》的像素级体验对标基线，再在此基础上全面超越；设计方向从一开始就允许超越，但任何创新不得以牺牲基础对标质量为代价。**

这是一款使用原创美术与原创实现的竖屏单机 RPG。对标对象用于定义体验基线，不用于复制受版权保护的素材、角色或具体表现资产。

### 阶段 A：像素级对标（基线达标前的首要目标）
- 按相同或可比的竖屏分辨率、设备安全区、游戏状态和镜头位置采集参考画面。
- 对主城/HUD、野外地图、角色比例与动作、队伍跟随、战斗反馈、探索迷雾、小地图、传送、任务成长逐模块建立对照样本。
- 逐项比较构图、占屏比例、元素位置与尺寸、信息层级、交互步骤、反馈时序和操作手感；使用同尺寸截图、透明度叠图、边缘/区域差异检查辅助验收。
- 每项差距必须形成“参考证据—当前表现—差距—修改—复测”的闭环；未采样的公开视频只列为待采样，不得假称已逐帧验证。
- 功能存在、脚本可解析或 CI 通过，都不能单独作为视觉/体验对标完成的证据。必须有可复核的实机截图或录屏验收。

### 阶段 B：全面超越（阶段 A 逐项达标后持续推进）
- 在已达标的操作习惯和信息架构上，提升地图探索深度、战斗策略、成长反馈、内容密度、性能、易用性与长期可玩性。
- 创新功能必须经过可玩性验证，不得破坏熟悉的核心循环、操作可读性或基础视觉品质。
- 超越项单独记录目标、验证方法和结果，不能用创新功能抵消尚未达标的基础模块。

### 模块验收矩阵
| 模块 | 阶段 A 对标基线 | 阶段 B 超越方向 | 完成证据 |
|---|---|---|---|
| 主城与 HUD | 竖屏构图、资源层级、图标入口、队伍与场景占比 | 更清晰的信息组织与个性化交互 | 同分辨率截图叠图、逐入口操作录屏 |
| 野外地图 | 地形、道路、地标、怪物/资源分布与镜头跟随 | 更丰富的区域生态、隐藏路线与动态事件 | 区域截图、路线实测、碰撞/可达性检查 |
| 角色与队伍 | 角色比例、队伍跟随、移动/攻击/受击反馈 | 更丰富的原创动作、队伍协同与职业差异 | 动作状态录屏、队形与遮挡检查 |
| 战斗与 Boss | 索敌、预警、范围、伤害反馈及可躲避性 | 更有层次的机制、连携与策略选择 | 同状态战斗录屏、命中/躲避回归 |
| 探索与地图界面 | 迷雾、探索度、小地图定位、怪物查看、传送闭环 | 多层探索目标、路线规划与区域事件 | 地图交互录屏、存档往返测试 |
| 成长与任务 | 任务引导、资源循环、英雄/装备成长反馈 | 更有深度且可持续的构筑与目标系统 | 完整新手/成长流程录屏、数据回归 |
| 音画与性能 | 反馈及时、画面统一、竖屏稳定运行 | 原创视听风格、稳定帧率与更佳适配 | 真机录屏、性能数据与设备覆盖 |

**统一判定规则：** 每个模块分别标记“未采样 / 有差距 / 实现中 / 代码验证通过 / 真机对标通过 / 超越验证通过”。只有“真机对标通过”才能计入阶段 A 完成；阶段 B 必须在阶段 A 证据基础上另行验收。不得把代码完成、CI 通过或 APK 成功导出写成像素级对标完成。

## 2. 参考游戏可观察到的核心体验

### 主城与 HUD
- 世界场景始终是主视觉中心，队伍角色在场景中可见。
- 顶部集中呈现多种资源和战力/等级信息。
- 功能入口以图标为主，分布在屏幕侧边；不是把所有功能压成底部一排文字按钮。
- 功能面板与主场景并存，入口层级清楚，不能遮住核心移动/战斗区域。

### 野外探索与地图
- 野外地图不是单一的纯色底板；应有可辨识的地形、道路、植被、地标、资源点、怪物和营地等空间信息。
- 探索过程逐步揭开迷雾，并记录区域探索度。
- 小地图应以玩家当前区域为中心/默认定位，提供区域切换、怪物定位和传送等交互。
- 区域推进需要由探索、任务、关卡门槛和传送点共同驱动；不能仅以击败一个 Boss 后强制自动切换整张地图替代探索。

### 战斗
- Boss 技能需要明确的预警阶段、地面范围提示、结算伤害和可读的安全区。
- 玩家移动必须能用于躲避技能；攻击、受击、技能和死亡反馈需要在画面上清楚可辨。
- 敌人、资源点和地形碰撞需要与视觉摆放一致，不能出现树木/地标挡住任务目标或路径的问题。

## 3. 当前项目与参考体验的差距（代码审查）

检查分支：`build/android-apk-from-tested-exploration-2026-11-05`

- `scripts/ui/hud.gd` 与 `scenes/main.tscn`：当前 HUD 主要是通用文字按钮和矩形标签。虽然已排成竖屏，但缺少参考游戏那种图标化侧边入口、资源信息层级和队伍/场景视觉优先级。**判定：未达到对标要求。**
- `scripts/core/map.gd`：当前野外地面主要由程序化纯色矩形、稀疏草线、少量路径线和固定树点构成；不是完整的地形/道路/地标/资源点场景。**判定：只完成了占屏与投影验证，不是最终地图实现。**
- `scripts/core/exploration_fog.gd`：已有按角色周围揭示网格迷雾并保存已探索格子的基础逻辑；但尚未看到与区域探索度 UI、小地图定位、怪物查看/传送的完整闭环。**判定：有底层雏形，产品体验未完成。**
- `scripts/core/world_map_manager.gd` 与 `scripts/core/main.gd`：区域解锁部分依赖 Boss/任务状态，且主线完成时自动切换地图。与参考游戏的迷雾探索、传送点和区域地图流程不等价。**判定：需要重新设计推进流程，避免自动切图替代探索。**
- `scripts/core/map.gd` 的树木和地标目前使用固定坐标数组，且树木统一使用绿色树纹理；场景主题、密度、路径与碰撞还需要逐区校验。**判定：需要美术与碰撞联合验收。**

## 4. 下一轮开发顺序（先验证体验，再扩写代码）

1. **实机基准采样**：按主城、野外普通探索、打开小地图、迷雾边界、传送点、Boss 预警六种状态，逐帧抽取公开视频/截图；记录画面尺寸、UI 安全区、元素边界、角色占屏比例、镜头与交互状态。
2. **地图与相机**：保留竖屏跟随相机，但以可探索的连续地图为目标；相机跟随、地图边界、出生点、地标和可行走区域必须同一坐标体系。
3. **迷雾与探索度**：完善已存在的迷雾系统，显示区域探索度；探索揭示应持久化，地图界面能看见未探索/已探索状态。
4. **小地图与传送**：实现当前区域默认定位、区域切换、怪物/地标定位和已解锁传送点快速传送。
5. **区域推进**：以任务目标、迷雾探索、关卡门槛和传送点共同解锁；完成任务后提示下一目标，不无条件强制切换地图。
6. **HUD**：重排为顶部资源与战力信息、侧边图标入口、底部战斗操作/摇杆安全区；所有按钮都要有对应图标与可用交互。
7. **战斗预警**：加入 Boss 蓄力提示、红色范围/扇形/直线预警、伤害结算和安全区验证。
8. **视觉验收**：每轮同时产出同分辨率本项目截图与参考画面对照；不以 headless 测试通过代替画面验收。

## 5. 本项目验收门槛

- [ ] 主城画面以原创场景和队伍角色为主体，HUD 不压住主要可玩区域。
- [ ] 资源、战力、等级信息清晰；主要功能入口图标化且可点击。
- [ ] 野外地图有连续可读的地形、道路、植被、地标、怪物和资源点。
- [ ] 角色移动时相机稳定跟随，地图边缘不露空，摇杆四向移动与屏幕方向一致。
- [ ] 迷雾随探索揭示，退出/重进后探索记录保留，并显示区域探索度。
- [ ] 小地图默认定位当前区域，可定位怪物/地标并传送到已解锁传送点。
- [ ] 区域推进由任务与探索门槛驱动，任务完成不会无提示地强制切图。
- [ ] Boss 技能预警清晰，玩家能通过移动躲避，命中/未命中反馈可见。
- [ ] 树木、地标、资源点和敌人的视觉位置、碰撞体、交互范围一致。
- [ ] Android 真机截图通过逐项对照后，才宣布该模块完成。

## 6. 开发原则

- 对标的是玩法结构、信息层级、镜头与交互体验；不复制《百炼英雄》的受版权保护美术素材。
- 先研究实机，再写设计基线，再改代码。
- 单元测试和 CI 证明逻辑/构建正确；不能证明画面体验符合对标。
- 未经真机画面验收，不把“已实现”写成“已达到参考品质”。
