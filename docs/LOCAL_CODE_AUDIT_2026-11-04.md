> 审查方式：Antigravity 批量只读读取脚本与数据文件，并分析汇总输出；未修改文件、配置、存档或 Git 历史。

## 1. 审查范围与限制

本轮覆盖项目目录结构、主场景与实体场景、核心 GDScript、Progression 管理器、UI 脚本、JSON 数据文件及项目配置。审查报告来自批量读取后汇总的 `output.txt`。

注意事项：

- 本报告中的部分行号来自汇总输出中的位置，**不是原始 GDScript 文件行号**；后续复核应以文件路径和函数名重新定位。
- “完整实现”“完全未引用”等措辞属于本轮工具审查的初步判断，必须结合调用链、运行时行为和 Godot 测试进一步确认。
- 本轮没有执行 Godot headless 检查、完整游戏回归、Android/iOS 导出或真机测试。
- 未检查所有 PNG 的像素内容；美术资源存在与运行时是否引用是两个不同问题。
- 本报告记录的是审查发现，不代表这些问题已经修复。

## 2. 项目结构概览

项目主要由以下部分组成：

- `project.godot`、`export_presets.cfg`：Godot 项目和 Android 导出配置。
- `scenes/`：主场景、英雄、普通敌人、Boss、营火和宝箱场景。
- `scripts/core/`：主流程、地图绘制、数据加载、本地存档。
- `scripts/character/`、`scripts/enemy/`、`scripts/interactable/`：英雄、敌人/Boss 与交互物逻辑。
- `scripts/progression/`：背包、营地、装备、等级、离线收益、任务、招募管理。
- `scripts/ui/`：HUD、虚拟摇杆及英雄、装备、背包、营地、离线、招募等面板。
- `data/`：英雄、敌人、任务、装备、掉落、等级、招募、营地、营火和离线收益 JSON。
- `assets/art-v1/`：英雄、怪物、Boss、装备和场景图集，以及单体 PNG。

整体结构以 `Main` 作为流程中枢，多个 Manager 承担数据和业务逻辑；UI 面板主要通过信号把操作请求交回 Main 处理。这种结构便于集中管理，但 Main 的职责较多，后续可在不破坏现有接口的前提下逐步拆分。

## 3. 当前主线功能盘点

### 3.1 角色、小队与战斗

第一轮代码阅读发现：

- 队长由虚拟摇杆或键盘方向输入控制；其他英雄按队形插槽跟随。
- 队友偏离队形目标一定距离后会主动归队，距离较远时有加速追赶逻辑。
- 治疗职业会周期性寻找生命比例较低的队友并治疗。
- 刺客具有周期性突进、目标选择和低血量目标额外伤害逻辑。
- 队长技能具有冷却，并对范围内敌人造成群体伤害。
- 英雄死亡后会延迟复活，复活时恢复部分生命值。
- 普通敌人具有周期性索敌、追击和攻击逻辑。
- Boss 具有生命阈值触发的第二阶段、攻击/移速强化、范围攻击预警，以及离开活动范围后返回出生点并恢复生命的逻辑。
- 普通敌人死亡后进入延迟刷新队列；Boss 是否刷新与普通怪物不同。

以上是代码结构层面的功能盘点，具体数值和平衡性尚未进行游戏内验证。

### 3.2 地图与镜头

- 当前 main 主线使用单一连续逻辑地图，尺寸为 1600×1200。
- 地图脚本绘制多个区域标记和地标，并根据 Boss/任务进度开放后续区域的怪物刷新。
- Hero、Enemy、Boss 各自存在硬编码的地图边界 clamp，范围约为 x=20..1580、y=20..1180。
- Camera2D 配置了平滑跟随和 1600×1200 边界；Main 每帧将镜头跟随队长。
- 当前营火交互没有真正的地图选择、地图切换或坐标传送闭环。

### 3.3 装备、背包与成长

- 装备以套装为单位切换；当前交互不是六个部位独立选择。
- 套装加成在英雄属性计算时叠加。
- 散件可以掉落并进入背包；背包满时会溢出到 mailbox。
- 散件目前主要用于分解换取金币；尚未形成独立穿戴和强化闭环。
- 等级/经验由独立管理器维护，并影响英雄属性成长。
- 离线收益基于本地系统时间戳计算，存在单机时钟可被修改的固有限制。

### 3.4 招募与任务

- 多名英雄通过初始解锁、任务完成或碎片合成加入队伍。
- 招募成功后有动态生成英雄并调整队形的逻辑。
- 任务包含击杀计数、Boss 击败和宝箱开启等目标，并与英雄解锁、区域开放存在关联。
- 第一轮报告尚未完整验证所有任务状态迁移、奖励发放、重复领取保护和异常存档恢复路径。

### 3.5 营地与离线收益

- 英雄管理建筑在初始状态可用。
- 铁匠铺、训练场等建筑具有建造成本和建造状态记录，但当前代码是否赋予持续玩法效果，初审判断为尚未形成完整闭环。
- 离线收益有最短离线阈值、最长结算封顶和金币/木材产出配置；使用本地时间，不能防止用户修改设备时钟。

## 4. 美术资源接入现状

第一轮审查报告称，`assets/art-v1/` 中包含：

- 5 张主要图集；
- 英雄、怪物、Boss、场景和散件等单体 PNG；
- 对应预览图和资源说明。

该报告通过检查场景节点和 GDScript 中的资源加载调用，初步判断当前 main 主线没有在 Hero、Enemy、Boss 和地图主体中引用这些 PNG，画面主体仍以 `_draw()` 的几何绘制为主。

**解释边界：**资源文件已经存在于仓库，不代表运行时已经显示；同样，未在抽样脚本中发现 `load()`/`preload()` 也不能替代全仓库资源引用搜索。后续应通过完整搜索、Godot Remote Scene Tree 和实际运行画面复核。

## 5. 存档结构与兼容性观察

初审记录的存档路径为：

- 主存档：`user://save.json`
- 备份：`user://save_backup.json`
- 当前 schema：Version 1

存档涉及金币、木材、时间戳、玩家位置、宝箱/Boss 状态、英雄生命值、背包/mailbox、营地、招募碎片、等级经验、任务和装备等数据。

初审报告描述了主档读取失败时尝试备份、写入前备份旧档的机制；但**本轮尚未通过故障注入验证原子写入、备份恢复和双档损坏后的行为**。

旧存档兼容性需要进一步核实，重点包括：

- 缺少 `recruitment`、`levels`、`last_saved_unix` 等字段时的默认值；
- 英雄当前 HP 是否从存档正确恢复，死亡/复活后是否正确保存；
- 招募碎片合成是否扣除碎片并在同一事务中更新招募状态；
- 存档结构升级时是否有明确 schema migration，而不是只修改版本号；
- 未来从 1600×1200 共享地图迁移到独立地图时，旧玩家位置如何转换。

## 6. 初审列出的风险与待验证项

以下分级是后续复核建议，不是已确认的缺陷严重度。

| 主题 | 初审观察 | 建议优先级 | 下一步验证 |
|---|---|---:|---|
| 怪物刷新容量 | 全队英雄与敌人共用 `MAX_UNITS=12` 的总量限制；满编后可能压缩可用怪物数量 | P0 / 高 | 检查所有生成、死亡、刷新、区域解锁调用链，构造满编队伍和目标怪被占满的场景 |

| 营火传送 | 当前只有解锁/提示逻辑，未形成可用传送流程 | P1 | 设计据点列表、解锁规则、传送落点和队伍整体移动 |

| 离线时间作弊 | 离线结算依赖本地系统时间 | P3（单机设计限制） | 决定是否接受单机可修改时间，或引入可信时间来源 |

### 6.1 特别说明：怪物刷新上限

初审指出：若 `heroes.size() + enemies.size() >= MAX_UNITS` 时跳过刷新，且队伍最多招募 6 名英雄，则怪物可用名额会被压缩。若其他区域或非任务怪持续占用名额，可能导致目标怪刷新延迟甚至任务无法推进。

该结论需要验证队列是否会持续重试、区域刷新是否有独立入口、实体计数是否包含已死亡/待删除节点，以及是否有其他清理策略。在这些检查完成前，应称为**潜在任务阻塞风险**，不应直接认定为必现永久卡死。

### 6.2 特别说明：性能风险

面板刷新时销毁并重建控件可能带来分配开销，但并不能仅凭代码模式断言会产生明显卡顿或频繁 GC。必须在目标设备或可比环境测量后再决定是否优化。

## 7. 后续工作顺序建议

不建议在核心逻辑未复核前，立即大规模接入美术或整合整个 2.5D 分支。

1. **核心逻辑交叉审查**：怪物刷新、招募碎片、英雄 HP、任务完成与奖励、存档恢复。
2. **世界坐标架构**：确定地图尺寸/坐标契约，统一 Hero/Enemy/Boss 边界；设计多地图与旧存档迁移。
3. **美术接入**：优先复用仓库已有 PNG，先静态接入，再安排动画；不重复生成已有资源。
4. **玩法闭环**：营火传送、营地建筑、装备散件、任务交付。
5. **移动端体验**：镜头构图、触控 UI、性能测量、Android/iOS 导出与设备验证。

## 8. 下一轮交叉审查清单

建议逐条跟踪以下调用链，形成“代码证据—复现条件—结论—修复方案”：

- `scripts/core/main.gd`：英雄生成、敌人生成与刷新队列、任务更新、招募合成、存档调用。
- `scripts/character/hero.gd`：HP 初始化、存档恢复、受伤、死亡、复活、保存。
- `scripts/core/save_manager.gd`：主档/备份写入、加载容错、schema 兼容。
- `scripts/progression/recruitment_manager.gd`：碎片增加、合成条件、扣除和已招募状态。
- `scripts/progression/quest_manager.gd`：任务计数、完成、奖励、防重复领取和解锁。
- `scripts/progression/backpack_manager.gd`：掉落、背包溢出、邮箱领取、分解。
- `scripts/core/map.gd` 与 Hero/Enemy/Boss：地图边界、装饰碰撞和生成点。
- 所有 UI 面板：显示互斥、关闭路径、刷新频率和控件重建。

## 9. 当前结论

Hero World main 已经具备可运行的单机 RPG 核心骨架，包括小队移动、自动战斗、职业差异、Boss 战、招募、任务、装备套装、背包、营地状态、离线收益和本地存档。与此同时，多地图传送、完整美术呈现、动画、建筑功能闭环和更丰富的装备系统仍需开发。

本轮报告的主要价值是建立了待验证问题清单。**下一步应先完成核心逻辑交叉审查，再开独立修复分支；本报告本身不包含代码修复，也不应作为功能已验收的依据。**
