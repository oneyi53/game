> **审查级别：静态审查，不等同于运行测试或功能验收。**

## 1. 审查范围与限制

本报告覆盖项目结构、主场景与实体场景、核心 GDScript、Progression 管理器、UI 脚本、JSON 数据文件及项目配置。第一轮由 Antigravity 批量读取后形成汇总；第二轮针对关键函数从 GitHub main 对应文件重新读取源代码，复核怪物刷新、招募、英雄 HP 和存档链路。

- 第一轮汇总输出中的行号不等于源文件行号；第二轮以文件路径和函数名定位。
- 本报告区分代码直接证实的缺陷、条件性风险和需要运行测试的事项。
- 未执行 Godot headless、完整游戏回归、Android/iOS 导出或真机测试。
- 本轮没有修改游戏代码、资源、项目配置或存档。

## 2. 项目结构概览

- `project.godot`、`export_presets.cfg`：Godot 项目和 Android 导出配置。
- `scenes/`：主场景、英雄、普通敌人、Boss、营火和宝箱场景。
- `scripts/core/`：主流程、地图绘制、数据加载、本地存档。
- `scripts/character/`、`scripts/enemy/`、`scripts/interactable/`：英雄、敌人/Boss 与交互物逻辑。
- `scripts/progression/`：背包、营地、装备、等级、离线收益、任务、招募管理。
- `scripts/ui/`：HUD、虚拟摇杆及英雄、装备、背包、营地、离线、招募等面板。
- `data/`：英雄、敌人、任务、装备、掉落、等级、招募、营地、营火和离线收益 JSON。
- `assets/art-v1/`：英雄、怪物、Boss、装备和场景图集，以及单体 PNG。

整体以 `Main` 作为流程中枢，多个 Manager 承担数据和业务逻辑；UI 面板通过信号把操作请求交回 Main 处理。Main 职责较多，后续可在不破坏现有接口的前提下逐步拆分。

## 3. 当前主线功能盘点

### 3.1 角色、小队与战斗

- 队长由虚拟摇杆或键盘方向输入控制；其他英雄按队形插槽跟随。
- 队友偏离队形目标一定距离后会主动归队，距离较远时加速追赶。
- 治疗职业周期性寻找生命比例较低的队友并治疗。
- 刺客具有周期性突进、目标选择和低血量目标额外伤害逻辑。
- 队长技能有冷却，并对范围内敌人造成群体伤害。
- 英雄死亡后延迟复活，复活时恢复部分生命值。
- 普通敌人具有周期性索敌、追击和攻击逻辑。
- Boss 具有生命阈值触发的第二阶段、攻击/移速强化、范围攻击预警，以及离开活动范围后返回出生点并恢复生命的逻辑。
- 普通敌人死亡后进入延迟刷新队列；Boss 不按普通怪物方式刷新。

### 3.2 地图与镜头

- main 主线使用单一连续逻辑地图，尺寸为 1600×1200。
- 地图脚本绘制多个区域标记和地标，并根据 Boss/任务进度开放后续区域怪物刷新。
- Hero、Enemy、Boss 各自存在硬编码地图边界 clamp，范围约 x=20..1580、y=20..1180。
- Camera2D 配置平滑跟随和 1600×1200 边界；Main 每帧跟随队长。
- 营火交互没有真正的地图选择、地图切换或坐标传送闭环。

### 3.3 装备、背包与成长

- 装备以套装为单位切换；当前不是六个部位独立选择。
- 套装加成在英雄属性计算时叠加。
- 散件可掉落并进入背包；背包满时溢出到 mailbox。
- 散件目前主要用于分解换金币，尚未形成独立穿戴和强化闭环。
- 等级/经验由独立管理器维护，并影响英雄属性成长。
- 离线收益基于本地系统时间戳计算，存在单机时钟可被修改的限制。

### 3.4 招募与任务

- 多名英雄通过初始解锁、任务完成或碎片合成加入队伍。
- 招募成功后有动态生成英雄并调整队形的逻辑。
- 任务包含击杀计数、Boss 击败和宝箱开启等目标，并与英雄解锁、区域开放关联。

### 3.5 营地与离线收益

- 英雄管理建筑在初始状态可用。
- 铁匠铺、训练场具有建造成本和建造状态记录，但尚未形成完整玩法效果闭环。
- 离线收益有最短离线阈值、最长结算封顶和金币/木材产出配置；使用本地时间，不能防止用户修改设备时钟。

## 4. 美术资源接入现状

`assets/art-v1/` 包含主要图集和英雄、怪物、Boss、场景、散件单体 PNG。第一轮检查场景节点和 GDScript 资源加载调用后，初步判断 main 主线角色和地图主体仍以 `_draw()` 几何绘制为主，现有 PNG 尚未挂接到主线主要实体。

资源存在不代表运行时显示；未在抽样脚本中发现加载调用也不能替代全仓库搜索。后续应通过完整引用搜索、Godot Remote Scene Tree 和实际运行画面复核。

## 5. 存档结构与兼容性

存档路径：
- 主存档：`user://save.json`
- 备份：`user://save_backup.json`
- 当前 schema：Version 1

数据包含金币、木材、时间戳、玩家位置、宝箱/Boss 状态、英雄生命值、背包/mailbox、营地、招募碎片、等级经验、任务和装备等。

第二轮核对发现：`SaveManager._try_load()` 只检查 JSON 可解析、根节点为 Dictionary、schema_version 等于 1；没有对业务字段进行完整结构校验。写入采用 `FileAccess.WRITE` 覆盖主档，不是严格的临时文件 + 原子替换流程。

## 6. 第二轮核心调用链交叉审查（2026-11-04）

复核基线：GitHub `main`，与本地审查报告记录的 `e194898` 对应。复核文件：`scripts/core/main.gd`、`scripts/core/save_manager.gd`、`scripts/character/hero.gd`、`scripts/progression/recruitment_manager.gd`、`scripts/progression/quest_manager.gd`、`scripts/progression/level_manager.gd`、`scripts/progression/backpack_manager.gd` 及相关 JSON。

### 6.1 已确认缺陷：英雄 HP 没有从存档恢复

证据链：
1. `Main._save_game()` 遍历当前英雄，将 `{id, hp}` 写入 `heroes` 数组。
2. `Main._spawn_heroes(save_data)` 读取玩家位置，但没有读取 `save_data["heroes"]` 并按 hero id 恢复 HP。
3. 英雄依次调用 `setup()`、`set_level()`、`reset_to_base_stats()`、`apply_equipment_bonus()`。
4. `Hero.setup()` 初始化 `hp=max_hp`；`Hero.apply_equipment_bonus()` 再次设置 `hp=max_hp`。

结论：重启后已招募英雄都会以满血状态生成，已保存的受伤 HP 被忽略。该问题由代码路径直接证实，尚未进行运行复现。

### 6.2 已确认缺陷：碎片合成没有消费碎片

证据链：
1. `Main._on_recruit_synthesize(hero_id)` 检查解锁类型、是否已招募和碎片数量。
2. 满足条件后调用 `recruitment_manager.recruit(hero_id)`。
3. 随后生成英雄、刷新 UI 并保存。
4. `RecruitmentManager` 具有 `add_fragment()`、`fragments_required()` 和 `recruit()`，但没有扣除碎片的消费方法；Main 合成回调也没有减少 `fragments`。

结论：合成成功后碎片数量仍保留在存档中。已招募标志阻止再次合成同一英雄，但资源消费规则没有闭环。

### 6.3 怪物刷新：原报告的“永久卡死”描述过强

证据链：
- `Main._tick_respawns()` 检查 `heroes.size() + enemies.size() >= MAX_UNITS`；满员时执行 `continue`，不会删除队列项。
- 到期计时器会继续保持非正值，后续帧仍会重试。
- 有空位时，遍历到期条目并生成怪物；成功生成后实体数增加。
- `_spawn_enemies()` 在区域解锁时把部分初始怪物种类放入刷新队列，且普通怪物死亡时再次入队。

结论：满员时队列项会等待空位，不是立即丢失；现有代码不足以证明任务怪永久无法刷新。仍存在待重生队列积压、同帧多条到期项争抢空位，以及持续高击杀速率下队列公平性/延迟问题。建议后续加入 FIFO 明确调度、队列长度/等待时间监控，并用满编队伍及多区域任务场景测试。原报告中“其他怪占位导致目标怪永远不重生”应修正为“可能延迟，需测试是否发生长期饥饿”。

### 6.4 已确认存档可靠性风险：备份可能被损坏主档覆盖

证据链：
1. `load_game()` 主档无效时会尝试备份；备份有效则返回 `restored_from_backup`，但没有立即修复主档或标记当前来源。
2. 后续 `save_game()` 只要发现主档文件存在，就把主档原文复制到备份。
3. 若主档损坏而备份原本有效，下一次保存会先用损坏主档覆盖有效备份，再写新主档。

结论：通常完整写入新主档后数据可恢复正常；但若在备份被覆盖后、新主档写完前发生写入失败/进程中断，原本有效的备份也已丢失。建议跟踪“从备份恢复”的状态，保存时先验证当前主档；并采用临时文件写入、校验、替换策略。需要故障注入验证具体文件系统行为。

### 6.5 存档结构校验与 schema 迁移风险

- `SaveManager._try_load()` 只验证 JSON 语法、Dictionary 根类型和 schema_version=1；不验证 gold、heroes、backpack、levels 等字段的类型和内部结构。
- 部分 Manager 会对单字段做宽松默认处理，但并非全局完整验证；格式错误可能在后续业务逻辑转换时引发运行时错误，或被默认值吞掉。
- 当前 schema 为 1。未来升级 schema 时必须先实现明确的逐版本迁移与失败策略，不能简单 bump 版本后把旧档当作损坏。



### 6.6 已确认状态判断缺陷：首次启动也会提示存档损坏

证据链：
1. `SaveManager._try_load()` 对不存在的文件返回 `ok=false`。
2. `SaveManager.load_game()` 在主档和备份均无效时，不区分文件不存在与文件存在但内容损坏，统一返回 `status="corrupted"`。
3. `Main._ready()` 收到 `corrupted` 时显示“存档损坏且无可用备份，从头开始”。
4. 因此首次安装、两个存档文件都尚未创建时，也会进入同一提示分支。

结论：首次启动可能出现误导性的存档损坏提示。建议增加 `new_game` / `not_found` 状态；只有至少存在一个存档文件且无法从主档/备份恢复时，才显示损坏警告。

## 8. 修复建议顺序

1. 修复英雄 HP 读档恢复；注意在等级/装备属性重算后再恢复 HP，并 clamp 到合法范围。
2. 增加招募碎片消费方法；先验证 recruit 成功，再原子扣除所需碎片并保存。
3. 修复 SaveManager：区分首次启动与双档损坏；避免损坏主档覆盖有效备份；加入主档有效性判断和安全替换流程。
4. 为怪物刷新队列制定明确 FIFO 策略并做满编任务测试；目前不应贸然改 MAX_UNITS。
5. 处理地图边界契约和旧存档迁移设计。
6. 再开展美术接入、传送和营地玩法闭环。
