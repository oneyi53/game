# 《百炼英雄》竞品研究与 Hero World 设计参考

> 日期：2026-11-04  
> 类型：设计研究 / 开发规划，不代表相关功能已经实现。  
> 项目基线：Hero World，Godot 4.7.2，竖屏 Android / iOS，原创单机 RPG。  
> 参考原则：学习成熟玩法的交互规律和系统组织方式，不复制其美术资产、角色、文案、数值或受版权保护的表现内容。

## 1. 研究目的与边界

本研究用于指导 Hero World 的玩法、画面和系统整合。参考信息来自公开游戏介绍、玩家攻略与用户提供的《百炼英雄》实机截图。公开资料适合确认玩法方向和系统构成，但不足以精确还原所有帧级表现、隐藏数值或版本差异。

以下内容分为三类：
- **可作为设计基线**：用户实机截图直接展示，或多个公开资料反复描述的操作/玩法特征。
- **待实机核验**：移动速度、摇杆半径、攻击间隔、跟随距离、技能前摇、镜头边界等具体参数。
- **Hero World 自主设计**：为单机体验、原创世界观和现有代码架构做出的取舍，不应误称为《百炼英雄》的原样机制。

## 2. 核心体验与循环

参考体验可概括为：

主城整备 → 进入野外 → 手动探索与走位 → 小队自动战斗 / 采集 / 事件 → 获得资源和奖励 → 英雄、装备、营地成长 → 解锁新区域或挑战 → 继续探索。

设计目标不是让玩家完全放置，而是把操作重点放在移动、站位、引怪、躲避危险、选择探索路线和队伍成长上；普通攻击可以自动化，以降低移动端操作负担。

## 3. 竖屏操作基线

用户提供的实机截图显示：游戏为竖屏，摇杆可以在屏幕下方的空白区域浮动出现；用户进一步明确，屏幕全域只要不与其他操作重叠，都可以调出摇杆。

Hero World 操作规格：
1. 保持竖屏基准，当前逻辑参考分辨率为 720×1280；适配不同设备时按安全区和视口比例布局。
2. 在**可操作的空白区域**按下时，以按下点为中心显示浮动摇杆；不限定为左下角或屏幕左半边。
3. UI 交互区域优先：按钮、菜单、背包、地图、资源入口、技能和其他明确交互控件不得同时触发移动摇杆。
4. 摇杆只绑定最初触发的触点 ID；其他手指可操作技能或 UI，不得改变摇杆方向。
5. 拖动控制队长移动；队员按队伍跟随规则跟进。
6. 触点释放、触摸取消、鼠标释放、窗口失焦等路径都必须清除输入；摇杆隐藏、移动向量归零。
7. 松手后角色停止主动移动，恢复自动攻击 / 采集等由游戏状态决定的行为。
8. 桌面调试支持鼠标按下、拖动和松开，且鼠标移出初始区域后释放也必须可靠清理。

实现顺序：先修复现有固定摇杆的释放残留问题，再改造为全屏空白区域浮动摇杆；分开提交，便于回归和定位问题。

## 4. 战斗与队伍

参考方向：
- 玩家主要控制队长走位，小队成员跟随。
- 普通敌人支持索敌、追击、攻击和死亡掉落；普通战斗以自动攻击为主。
- 精英敌人应有更强属性或清晰的特殊攻击。
- Boss 需要可读的技能过程：蓄力 / 预警 → 判定 → 伤害或控制 → 收招 / 冷却；可以逐步增加圆形、扇形、直线、持续区域等攻击类型。
- 队伍成员定位应有差异，例如承伤、输出、治疗或辅助；阵容搭配要对战斗产生可感知影响。
- 战斗反馈包含受击、伤害数字、技能特效、死亡和掉落反馈。

设计约束：
- 不把自动攻击误做成自动寻路或完全自动通关。
- 玩家移动、拉扯和躲避必须有价值。
- Boss 预警必须能在竖屏战斗画面中辨识，避免被角色、树木、数字和 UI 遮挡。
- 复杂机制分阶段实现，不一次性堆叠大量技能。

## 5. 地图、探索与交互

地图不应只是战斗背景，而应由道路、地形、装饰、敌人、资源点、宝箱、营地 / 传送点、事件和区域边界共同构成。

可借鉴的探索行为：
- 手动移动探索，而非依赖自动寻路。
- 通过迷雾或区域门槛呈现探索进度。
- 砍树、挖矿、采集和开启宝箱，让地图资源有明确用途。
- 通过救援 / 招募事件扩展英雄阵容。
- 通过传送点连接已经解锁的区域。
- 让资源点、敌人和事件在空间上形成探索路线，而非随机散布。

Hero World 当前差距（来自此前静态审查，仍需运行验证）：
- 当前主线地图为单一连续地图；营火传送尚未形成真正的区域切换闭环。
- 树木 / 地标缺少完整阻挡与碰撞表现。
- 采集、传送、地图解锁等部分流程尚未全部落到可操作玩法。
- 已有美术 PNG 资源尚未被主线场景和脚本完整引用。

## 6. 资源与成长循环

参考设计应让资源来源和用途形成闭环，而不是只在 HUD 上显示数字。

资源类型可包括金币、食物 / 肉类、木材、矿石和稀有招募材料等。每种资源都应有：
- 清晰来源：战斗掉落、采集、宝箱、任务或离线收益。
- 清晰用途：升级、装备、建筑、区域解锁、招募或其他养成。
- 消耗反馈：升级成功、解锁新功能、容量变化或战力提升。
- 存储与溢出规则：上限、满仓提示、奖励领取规则。
- 存档一致性：消耗和奖励要原子化处理，避免重复领取或只校验不扣除。

成长层次：
1. 英雄：等级、基础属性、技能。
2. 队伍：招募、上阵、职业定位、协同。
3. 装备：散件获取、穿戴、属性、强化 / 分解。
4. 营地：铁匠铺、训练场等建筑必须提供真实且可见的玩法收益。
5. 地图：区域、传送点、Boss、资源点和探索进度。
6. 长期目标：更高难度区域、更强敌人、更完整队伍和装备追求。

Hero World 不必照搬对标游戏的付费、联网、活动或数值体系。作为单机 RPG，应优先保证资源来源透明、成长反馈明确、离线收益可控、存档可靠。

## 7. 画面与表现规范

目标方向：卡通斜视伪 2.5D、竖屏、清晰的角色轮廓和丰富但有秩序的场景层次。

建议分层：
1. 地面底图与道路。
2. 地表细节和不可交互装饰。
3. 可交互资源点 / 建筑。
4. 角色与敌人，按 Y / 深度规则排序。
5. 前景遮挡物（树冠、屋檐等），必要时采用前后拆分。
6. 技能预警、伤害数字和战斗特效。
7. HUD 与菜单 UI。

质量要求：
- 角色和敌人不能被不合理的装饰遮挡。
- 树干、岩石、建筑等应按需要提供碰撞或导航阻挡。
- 资源点要有状态反馈（可采集、采集中、已耗尽 / 冷却）。
- 技能预警需高对比且留有反应时间。
- HUD 保持竖屏单手可达，战斗中心区域尽量留白。
- 优先接入仓库已有原创 PNG / 图集，不重复制作已有资产。
- 图片资源存在不等于游戏已经使用；验收需确认实际运行画面引用了对应资源。

## 8. Hero World 当前开发优先级

### P0：操作稳定性
- 修复摇杆松手后偶尔持续移动。
- 实现全屏空白区域浮动摇杆和 UI 命中优先级。
- 正确处理多点触控、触摸取消、窗口失焦和鼠标释放。
- 验证队长移动、队员跟随、松手停止、自动攻击恢复。

### P1：美术接入与地图表现
- 接入现有原创角色、敌人、Boss、装备和场景素材。
- 建立地面 / 装饰 / 交互物 / 角色 / 前景遮挡的渲染层次。
- 修复树木、岩石和地标的碰撞阻挡。
- 调整竖屏镜头跟随、边界和 UI 遮挡。

### P2：探索闭环
- 采集、宝箱、救援事件和资源掉落真正可玩。
- 实现区域解锁、迷雾 / 地图进度和真实传送。
- 让不同地图区域拥有差异化敌人、资源和奖励。

### P3：战斗深度
- 完善自动索敌、队伍跟随和职业定位。
- 建立通用 Boss 技能预警 / 判定框架。
- 增加精英怪与 Boss 阶段机制，保证技能可读性。

### P4：成长闭环
- 完善散件装备穿戴和分解。
- 让铁匠铺、训练场提供真实效果。
- 确保招募碎片扣除、资源消耗、奖励发放和存档一致。
- 检查离线收益时间篡改和资源上限策略。

### P5：整体打磨
- 主城与野外区域切换。
- 任务、奖励、离线收益和存档体验。
- Android / iOS 竖屏适配、性能和真机测试。

## 10. 实施与版本控制约束

- 唯一正式主线仍为 main。
- 每个阶段使用独立 feature / fix 分支和 PR。
- 不直接在 main 上开发，不覆盖用户本地项目或 FantasyRPG 临时目录。
- 合并前检查当前 main、PR #6 / #7 状态及文件冲突。
- 保持 JSON 和存档结构兼容；确需迁移时增加版本化迁移和旧档测试。
- 先做小步修改和可回滚提交，再进行跨系统整合。
- PR 描述必须区分静态审查、脚本解析、Godot 运行、功能回归和真机验证。
- 不把尚未验证的研究结论写成已实现功能。

## 12. 用户补充截图拆解：主城、英雄编队、任务与 UI（2026-11-04）

本节吸收本轮新增的截图观察。截图中出现的建筑名称、英雄数量、战力数值、任务次数和奖励档位均属于对标游戏样本，不直接成为 Hero World 的配置或数值。

### 12.1 参考观察与本项目取舍

| 参考观察 | 可学习的设计规律 | Hero World 当前判断 |
|---|---|---|
| 2.5D 主城与多个功能建筑 | 建筑承担功能入口，减少纯菜单层级 | 已有独立「王朝营地」地图；现有营地/招募/背包/装备等系统面板存在，但截图式招募大厅、黑市、圣辉宝阁、守护兽、女神像等完整建筑交互尚未形成 |
| 悬浮活动按钮与红点 | 只在存在可领取/可处理事项时显示提醒；点击后应能定位到具体内容 | 当前 HUD 与面板入口已存在；尚未核实有统一 RedDotManager/红点数据流，不把装饰性红点视为系统完成 |
| 英雄收集与上阵编队 | 收集库存、当前出战队伍、队伍上限应是不同概念 | 当前有英雄招募/等级/队伍跟随与自动战斗；完整的「英雄图鉴库存—上阵槽位—替换—队伍上限」闭环仍需审查与补齐 |
| 单英雄战力与总战力 | 战力由基础属性、等级、装备、建筑加成等统一计算 | 当前英雄属性重算已包含等级、装备、营地增益等路径；独立且可解释的战力评分/总战力 HUD 尚未作为完整系统验收 |
| 碎片合成 | 合成成功必须原子扣除对应碎片，失败不能扣除 | 招募/碎片消费逻辑已有修复来源；仍应以当前 main 代码和回归测试核验，不引用样本中的 2741/30 数字 |
| 日常任务活跃度宝箱 | 任务目标、活跃度累计、分段奖励、领取状态分离 | 当前已有任务管理/进度存档基础；截图式日常任务列表、20/50/70/90/110 活跃度阶梯奖励不是当前已验收功能 |
| 半透明遮罩与居中卡片 | 弹窗统一层级、遮罩、关闭规则和互斥关系 | 当前已有多面板互斥修复；应继续统一弹窗视觉规范，不复制对标游戏的具体皮肤和图标 |

### 12.2 原创系统建议

**主城建筑入口**：把建筑表现与系统逻辑分开。建筑节点只负责世界中的位置、点击热区、名称和开放状态；点击后由 UI 路由打开对应系统面板。建筑数据建议包含 `building_id`、显示名称、开放条件、入口面板、交互范围和视觉资源引用。未开放建筑可显示条件，但不能提前调用未实现的系统。

**英雄编队**：明确区分：
- 英雄收藏：玩家已拥有的英雄及其等级、星级/突破、碎片；
- 出战编队：当前地图实际生成并参与战斗的英雄；
- 队伍上限：由规则配置控制，不从截图直接固定为 10；
- 跟随表现：仅是编队的空间表现，不应成为英雄数据本体。

编队数据应由稳定的 hero_id 列表表示；换位、上阵、下阵需要校验拥有状态、槽位上限、重复英雄和存档一致性。跟随偏移只影响表现与移动目标，不应修改英雄 ID 或战斗属性。

**战力计算**：建立单一的 `PowerCalculator` 或等价纯计算函数，输入英雄基础属性、等级成长、装备、营地加成和已启用被动，输出可复算的英雄战力；总战力只对当前出战编队求和。不要在 UI 中散落重复公式。战力是展示指标，不应替代真实伤害/承伤公式。

**任务与红点**：任务状态至少区分未开始、进行中、可领取、已领取；活跃度是任务奖励状态之外的汇总值。红点由系统状态派生，例如「有奖励可领」「有空编队槽且有可上阵英雄」「建筑可升级」，不允许通过 UI 点击直接永久清除。点击入口后应打开对应目标页，状态变化后自动刷新。

### 12.3 UI 与美术资产规范

- 原创卡通奇幻风格可以采用高对比轮廓、清楚的按钮状态和有限的高光描边；具体颜色、形状、纹样、图标和字体应建立 Hero World 自己的视觉规范。
- 弹窗统一使用背景遮罩、内容卡片、标题区、关闭控件、主要/次要操作区；不同面板复用布局组件，不复用对标游戏的独有装饰。
- 资源栏、红点、角标、按钮按下态、禁用态、加载态和奖励领取态都应有独立状态图。
- PNG、图集或骨骼动画只是资产交付格式选择。项目当前已接入 PNG 精灵与原创特效图集；不能据此推断当前项目使用 Spine，也不要求为了模仿 H5 架构而改用 Cocos/Laya。
- 资产登记需记录来源、授权/原创状态、尺寸、锚点、用途、导入设置和引用路径；本项目只使用原创或明确可合法使用的资源。

### 12.4 H5 技术观察如何映射到 Godot

用户提供的 Cocos Creator / Laya / Egret、SpriteAtlas、Spine、JSON 配表、Manager 单例和浏览器 Network 面板等内容，属于 H5 项目常见技术线索，不是对《百炼英雄》实际内部实现的确认，也不是 Hero World 的技术选型要求。

Hero World 的对应实现边界：
- 场景与节点：Godot Scene/Node，按主场景、地图、单位、交互物和 UI 拆分；
- 数据配置：仓库 `data/*.json` 与 DataLoader/各 Manager；配置校验失败应明确停止，不用静默默认值掩盖错误；
- 地图逻辑：`WorldMapManager` 提供地图 ID、地图尺寸、出生点、敌人归属和边界；
- 2.5D 绘制：`WorldProjection` 只负责逻辑坐标到屏幕坐标转换，不写回角色逻辑位置；
- 英雄跟随：当前 `Hero` 使用队长位置与 formation_offset 计算跟随目标；这是轻量跟随，不应宣称已实现完整 Flocking 群聚寻路；
- 存档：`SaveManager` 负责本地 JSON 主档/备份，Main 负责加载后迁移与写回；本项目是单机本地存档，不引入对标游戏的网络协议或服务端假设。

## 13. 2026-11-05 用户确认：以《百炼英雄》作为硬性体验基准

用户明确要求“完全按照对标做”。本项目执行口径调整为：玩法体验、系统完整度、地图探索密度、镜头与角色反馈、战斗节奏和移动端操作均以《百炼英雄》作为验收参照；不再以“有入口/有面板/能移动”作为完成标准。仅学习可观察的设计规律，不复制其代码、角色、美术资产、UI 独特表达、文案或具体数值。

### 强制验收维度
1. **地图尺度与探索**：区域必须足以形成连续探索路线，包含可辨识地形分区、道路/岔路、阻挡、地标、资源点、宝箱、营地/传送点、敌群与精英/Boss 区；探索不是在 1200×900 小场地里稀疏摆点。地图尺度必须结合竖屏实际视野、投影、相机缩放和移动速度共同设计，不能只放大 bounds 数字。
2. **镜头与空间**：队长移动时相机平滑跟随，边界正确夹取；地面、角色、敌人、树木/建筑和前景遮挡采用统一投影与 Y 深度排序；碰撞形状与视觉脚底锚点一致。
3. **角色表现**：静态 PNG 不得冒充动画。至少建立可辨识的待机、行走、转向/朝向反馈；战斗阶段再补攻击、受击、技能动作。移动应有起步/减速、脚步节奏、队伍跟随和停止反馈，消除“飘移感”。
4. **探索循环**：迷雾/区域发现、探索度、资源采集、宝箱、营地恢复/复活、传送网络、任务事件和区域解锁形成真实闭环。
5. **战斗循环**：普通攻击自动化与玩家手动走位并存；敌人有感知/追击/攻击范围，精英与 Boss 有可读预警、躲避空间和阶段差异；击败后奖励进入成长循环。
6. **移动端验收**：竖屏触控、全屏浮动摇杆、多点触控、UI 热区优先、不同宽高比与真实设备帧率均需单独验收。

### 当前代码事实（main 静态审查）
- `WorldMapManager.MAP_SIZE` 当前为 1200×900，四张地图共用同一尺寸。
- `MapDrawer` 以 64 单位方格铺底，森林地图仅配置少量固定树木/地标；这不足以达到目标探索密度。
- `Hero._physics_process()` 当前队长直接 `velocity = move_input * move_speed`；队员按固定偏移追随。
- `Hero._draw()` 当前直接绘制单张 96×96 英雄 PNG，没有行走/待机/攻击/受击帧动画状态机。`SPRITE_SPEC.md` 登记的英雄 PNG 为 512×512 单张透明画布，不能从静态图推断已有动画帧。
- `WorldProjection` 当前投影常量固定基于 1200×900，扩大地图前必须先把投影、地图边界、镜头、装饰、碰撞、敌人出生点和存档坐标统一改为地图数据驱动。

以上为静态源码结论，尚未进行 Godot 实机运行验证。
