# 《百炼英雄》竞品研究与 Hero World 设计参考

> 日期：2026-11-04  
> 类型：设计研究 / 开发规划，不代表相关功能已经实现。  
> 项目基线：Hero World，Godot 4.7.2，竖屏 Android / iOS，原创单机 RPG。  
> 参考原则：学习成熟玩法的交互规律和系统组织方式，不复制其美术资产、角色、文案、数值或受版权保护的表现内容。

## 1. 研究目的与边界

本研究用于指导 Hero World 的玩法、画面和系统整合。参考信息来自公开游戏介绍、玩家攻略与用户提供的《百炼英雄》实机截图。公开资料适合确认玩法方向和系统构成，但不足以精确还原所有帧级表现、隐藏数值或版本差异。

以下内容分为三类：
- **可作为设计基线**：用户实机截图直接展示，或多个公开资料反复描述的操作/玩法特征。
- **待实机核验**：移动速度、摇杆半径、攻击间隔、跟随距离、技能前摇、镜头边界等具体参数。
- **Hero World 自主设计**：为单机体验、原创世界观和现有代码架构做出的取舍，不应误称为《百炼英雄》的原样机制。

## 2. 核心体验与循环

参考体验可概括为：

主城整备 → 进入野外 → 手动探索与走位 → 小队自动战斗 / 采集 / 事件 → 获得资源和奖励 → 英雄、装备、营地成长 → 解锁新区域或挑战 → 继续探索。

设计目标不是让玩家完全放置，而是把操作重点放在移动、站位、引怪、躲避危险、选择探索路线和队伍成长上；普通攻击可以自动化，以降低移动端操作负担。

## 3. 竖屏操作基线

用户提供的实机截图显示：游戏为竖屏，摇杆可以在屏幕下方的空白区域浮动出现；用户进一步明确，屏幕全域只要不与其他操作重叠，都可以调出摇杆。

Hero World 操作规格：
1. 保持竖屏基准，当前逻辑参考分辨率为 720×1280；适配不同设备时按安全区和视口比例布局。
2. 在**可操作的空白区域**按下时，以按下点为中心显示浮动摇杆；不限定为左下角或屏幕左半边。
3. UI 交互区域优先：按钮、菜单、背包、地图、资源入口、技能和其他明确交互控件不得同时触发移动摇杆。
4. 摇杆只绑定最初触发的触点 ID；其他手指可操作技能或 UI，不得改变摇杆方向。
5. 拖动控制队长移动；队员按队伍跟随规则跟进。
6. 触点释放、触摸取消、鼠标释放、窗口失焦等路径都必须清除输入；摇杆隐藏、移动向量归零。
7. 松手后角色停止主动移动，恢复自动攻击 / 采集等由游戏状态决定的行为。
8. 桌面调试支持鼠标按下、拖动和松开，且鼠标移出初始区域后释放也必须可靠清理。

实现顺序：先修复现有固定摇杆的释放残留问题，再改造为全屏空白区域浮动摇杆；分开提交，便于回归和定位问题。

## 4. 战斗与队伍

参考方向：
- 玩家主要控制队长走位，小队成员跟随。
- 普通敌人支持索敌、追击、攻击和死亡掉落；普通战斗以自动攻击为主。
- 精英敌人应有更强属性或清晰的特殊攻击。
- Boss 需要可读的技能过程：蓄力 / 预警 → 判定 → 伤害或控制 → 收招 / 冷却；可以逐步增加圆形、扇形、直线、持续区域等攻击类型。
- 队伍成员定位应有差异，例如承伤、输出、治疗或辅助；阵容搭配要对战斗产生可感知影响。
- 战斗反馈包含受击、伤害数字、技能特效、死亡和掉落反馈。

设计约束：
- 不把自动攻击误做成自动寻路或完全自动通关。
- 玩家移动、拉扯和躲避必须有价值。
- Boss 预警必须能在竖屏战斗画面中辨识，避免被角色、树木、数字和 UI 遮挡。
- 复杂机制分阶段实现，不一次性堆叠大量技能。

## 5. 地图、探索与交互

地图不应只是战斗背景，而应由道路、地形、装饰、敌人、资源点、宝箱、营地 / 传送点、事件和区域边界共同构成。

可借鉴的探索行为：
- 手动移动探索，而非依赖自动寻路。
- 通过迷雾或区域门槛呈现探索进度。
- 砍树、挖矿、采集和开启宝箱，让地图资源有明确用途。
- 通过救援 / 招募事件扩展英雄阵容。
- 通过传送点连接已经解锁的区域。
- 让资源点、敌人和事件在空间上形成探索路线，而非随机散布。

Hero World 当前差距（来自此前静态审查，仍需运行验证）：
- 当前主线地图为单一连续地图；营火传送尚未形成真正的区域切换闭环。
- 树木 / 地标缺少完整阻挡与碰撞表现。
- 采集、传送、地图解锁等部分流程尚未全部落到可操作玩法。
- 已有美术 PNG 资源尚未被主线场景和脚本完整引用。

## 6. 资源与成长循环

参考设计应让资源来源和用途形成闭环，而不是只在 HUD 上显示数字。

资源类型可包括金币、食物 / 肉类、木材、矿石和稀有招募材料等。每种资源都应有：
- 清晰来源：战斗掉落、采集、宝箱、任务或离线收益。
- 清晰用途：升级、装备、建筑、区域解锁、招募或其他养成。
- 消耗反馈：升级成功、解锁新功能、容量变化或战力提升。
- 存储与溢出规则：上限、满仓提示、奖励领取规则。
- 存档一致性：消耗和奖励要原子化处理，避免重复领取或只校验不扣除。

成长层次：
1. 英雄：等级、基础属性、技能。
2. 队伍：招募、上阵、职业定位、协同。
3. 装备：散件获取、穿戴、属性、强化 / 分解。
4. 营地：铁匠铺、训练场等建筑必须提供真实且可见的玩法收益。
5. 地图：区域、传送点、Boss、资源点和探索进度。
6. 长期目标：更高难度区域、更强敌人、更完整队伍和装备追求。

Hero World 不必照搬对标游戏的付费、联网、活动或数值体系。作为单机 RPG，应优先保证资源来源透明、成长反馈明确、离线收益可控、存档可靠。

## 7. 画面与表现规范

目标方向：卡通斜视伪 2.5D、竖屏、清晰的角色轮廓和丰富但有秩序的场景层次。

建议分层：
1. 地面底图与道路。
2. 地表细节和不可交互装饰。
3. 可交互资源点 / 建筑。
4. 角色与敌人，按 Y / 深度规则排序。
5. 前景遮挡物（树冠、屋檐等），必要时采用前后拆分。
6. 技能预警、伤害数字和战斗特效。
7. HUD 与菜单 UI。

质量要求：
- 角色和敌人不能被不合理的装饰遮挡。
- 树干、岩石、建筑等应按需要提供碰撞或导航阻挡。
- 资源点要有状态反馈（可采集、采集中、已耗尽 / 冷却）。
- 技能预警需高对比且留有反应时间。
- HUD 保持竖屏单手可达，战斗中心区域尽量留白。
- 优先接入仓库已有原创 PNG / 图集，不重复制作已有资产。
- 图片资源存在不等于游戏已经使用；验收需确认实际运行画面引用了对应资源。

## 8. Hero World 当前开发优先级

### P0：操作稳定性
- 修复摇杆松手后偶尔持续移动。
- 实现全屏空白区域浮动摇杆和 UI 命中优先级。
- 正确处理多点触控、触摸取消、窗口失焦和鼠标释放。
- 验证队长移动、队员跟随、松手停止、自动攻击恢复。

### P1：美术接入与地图表现
- 接入现有原创角色、敌人、Boss、装备和场景素材。
- 建立地面 / 装饰 / 交互物 / 角色 / 前景遮挡的渲染层次。
- 修复树木、岩石和地标的碰撞阻挡。
- 调整竖屏镜头跟随、边界和 UI 遮挡。

### P2：探索闭环
- 采集、宝箱、救援事件和资源掉落真正可玩。
- 实现区域解锁、迷雾 / 地图进度和真实传送。
- 让不同地图区域拥有差异化敌人、资源和奖励。

### P3：战斗深度
- 完善自动索敌、队伍跟随和职业定位。
- 建立通用 Boss 技能预警 / 判定框架。
- 增加精英怪与 Boss 阶段机制，保证技能可读性。

### P4：成长闭环
- 完善散件装备穿戴和分解。
- 让铁匠铺、训练场提供真实效果。
- 确保招募碎片扣除、资源消耗、奖励发放和存档一致。
- 检查离线收益时间篡改和资源上限策略。

### P5：整体打磨
- 主城与野外区域切换。
- 任务、奖励、离线收益和存档体验。
- Android / iOS 竖屏适配、性能和真机测试。

## 9. 验收清单

### 操作
- [ ] 在多个空白区域按下均可出现浮动摇杆。
- [ ] 在技能、背包、地图、菜单等 UI 上按下不会触发摇杆。
- [ ] 单指拖动稳定，方向和距离正确。
- [ ] 多指操作时摇杆只跟踪原触点。
- [ ] 控件内松开、控件外松开、触摸取消和失焦均能停止移动。
- [ ] 鼠标桌面测试与触屏行为一致。
- [ ] 松手后队长停止，自动攻击状态正确恢复。

### 画面与地图
- [ ] 实际运行画面加载原创素材，而不是仅显示程序绘制的占位图形。
- [ ] 角色、敌人、树木和建筑的遮挡关系正确。
- [ ] 树干 / 岩石等阻挡符合视觉直觉。
- [ ] Boss 预警在竖屏上清楚可见。
- [ ] HUD 不遮挡关键战斗区域。

### 系统
- [ ] 资源获取和消耗有完整闭环。
- [ ] 传送确实改变区域 / 场景状态。
- [ ] 装备穿戴、分解和属性变化一致。
- [ ] 建筑升级带来可验证收益。
- [ ] 招募、奖励和存档不会重复发放或漏扣资源。

每一项必须记录测试环境、Godot 版本、设备 / 输入方式、结果和证据。静态审查不能代替运行测试；桌面鼠标测试不能代替移动设备触屏测试。

## 10. 实施与版本控制约束

- 唯一正式主线仍为 main。
- 每个阶段使用独立 feature / fix 分支和 PR。
- 不直接在 main 上开发，不覆盖用户本地项目或 FantasyRPG 临时目录。
- 合并前检查当前 main、PR #6 / #7 状态及文件冲突。
- 保持 JSON 和存档结构兼容；确需迁移时增加版本化迁移和旧档测试。
- 先做小步修改和可回滚提交，再进行跨系统整合。
- PR 描述必须区分静态审查、脚本解析、Godot 运行、功能回归和真机验证。
- 不把尚未验证的研究结论写成已实现功能。

## 11. 研究局限与后续补充

本文件是第一版桌面研究结论。公开页面和玩家攻略可能存在版本差异；精确操作参数、地图坐标、敌人 AI、Boss 机制数值、掉落概率和经济曲线需要进一步实机记录。后续如取得更完整的实机录屏，可补充逐项流程图、UI 安全区域、操作热区、镜头参数和关卡节奏分析。
