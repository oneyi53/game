# 英雄编队数据层

## 目标

把“已拥有英雄”和“当前出战英雄”分开管理。招募系统仍负责英雄归属、碎片与解锁；编队系统维护出战名单、槽位顺序和队伍上限。

## 当前阶段边界

本阶段只交付纯数据层与回归测试，**尚未接入 Main 的英雄生成、面板交互或存档写入**。因此不会改变当前玩家实际队伍，也不会改变旧存档行为。下一阶段在独立 PR 中接入 UI 和运行时生成。

## 数据契约

存档可选字段：

- `formation.active_ids`：按槽位顺序排列的已拥有英雄 ID 数组；第一个 ID 即当前队长。
- 队伍上限由代码中的 `DEFAULT_MAX_PARTY_SIZE` 配置，当前为 4，不从存档读取。

示例：

```json
{
  "formation": {
    "active_ids": ["archer", "guardian", "healer"]
  }
}
```

## 规则

- 任意已拥有英雄均可担任队长；当前队长由 `active_ids[0]` 决定，不绑定固定英雄 ID。
- 可以将已上阵英雄调到首槽；也可以直接从预备名单提拔为队长。
- 队伍已满时，预备英雄提拔为队长会替换当前首槽英雄，原队长自动进入预备名单。
- 可以下阵任何英雄，包括当前队长；下阵队长后，下一位队员自动成为队长。
- 至少保留一名出战英雄，避免出现无队伍状态。
- 不能上阵未拥有英雄或重复英雄；达到队伍上限后不能继续添加。
- 任意槽位均可交换，交换到首槽即更换队长。
- 存档读取时过滤未知/重复/未拥有 ID；若过滤后没有有效成员，则以第一名已拥有英雄作为初始队长。
- 默认上限为 4，是 Hero World 当前阶段的原创平衡参数，不引用对标截图中的 10 人队伍。

## 下一阶段

1. 将 RecruitmentManager 的拥有列表传入 FormationManager。
2. Main 只生成 active_ids 对应英雄；英雄收藏/招募仍显示全部 owned_ids。
3. 装备、等级和英雄详情面板支持收藏英雄（包括暂不上阵的英雄）。
4. 上阵、下阵、换位、换队长成功后保存 formation 字段，并刷新队伍与面板。
5. 验证旧存档首次迁移、招募后可上阵、退队后仍保留装备/等级/碎片，以及 MAX_UNITS 约束。


## 第二阶段：运行时与编队界面（PR #36，Godot CI 通过）

- Main 初始化 FormationManager：已拥有列表来自 RecruitmentManager，存档 `formation.active_ids` 优先；旧存档缺少编队字段时按原英雄顺序迁移，最多取 4 人。
- 世界中只生成当前上阵英雄；第一个上阵槽位是真正的可控队长，队长 ID 不再写死为 `captain`。
- 英雄面板增加编队名单，可设置队长、上阵和下阵；满编时可直接把预备英雄提拔为队长并替换原队长。
- 编队变更后重建队伍节点，刷新跟随关系、装备面板和背包英雄引用，并保存编队 ID 列表。
- 等级、经验、套装与散件装备仍按 hero_id 独立保存在管理器中；非上阵英雄不会因节点未生成而丢失这些养成数据。
- 英雄 HP 使用独立缓存，编队切换及保存时保留预备英雄最近一次 HP；首次加入收藏但从未上阵的英雄按满血初始化。
- 当前界面已支持上阵/下阵/更换队长；预备英雄的装备操作入口和真机视觉验收仍需后续补齐。
