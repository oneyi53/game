# 每日活跃度与统一红点系统设计方案

> 状态：技术设计提案，未实现。基线：`main`，静态核对提交 `2d2c158e309d607bdee1868f14f7b4e2068d53af`（2026-11-04）。本文件仅记录现状、待决策事项和建议接口；不修改玩法、存档、UI、数据或 CI。

## 1. 目标与边界

为未来每日任务/活跃度面板准备可验证的 UI 与状态测试方案，并提出全局红点派生架构。该提案不宣称每日活跃度、领奖状态、每日重置或 `RedDotManager` 已存在，也不应作为未经确认的接口契约。

约束：

- 保持 `main` 不变；本文档本身不实现任何功能。
- 未来实现必须先由产品确认每日规则与时区，再设计可选存档扩展并单独审查；不得在本设计 PR 中改存档格式。
- 不新建“已完成/可领取”等 UI 自维护状态，除非它们是权威核心状态的纯展示缓存，并能被重新计算。
- 不引入第三方代码、素材或依赖。

## 2. 当前代码结构与已核实能力

### 2.1 任务系统

`data/quests.json` 当前列出 9 个固定任务：Boss、击杀计数和宝箱计数目标；字段含任务名、目标、目标计数、对话文本与 `reward_gold`。其中 8 个任务配置非零金币奖励，主线 Boss 任务为 0。

`scripts/progression/quest_manager.gd`：

- `load_quests()` 读取并校验 `data/quests.json`，为每个任务初始化 `counts`、`completed`。
- `on_enemy_killed()` 按目标敌人 ID 增加击杀数；Boss 任务还要求 `is_boss`，配置了 `target_id` 时必须匹配。
- `on_chest_opened()` 更新宝箱目标。
- 达到条件后 `_complete()` 将完成标记设为真并发出 `quest_completed(quest_id, name, line, reward_gold)`。
- 已完成任务忽略后续事件。`load_progress()` 对负计数下限裁为 0，忽略未知任务 ID；没有按目标上限裁剪正计数。
- `save_progress()` 返回 `{counts, completed}`；没有每日任务、活跃度积分、每日重置、奖励领取标记或单独领取接口。

`scripts/core/main.gd` 在启动时加载任务进度，在 `quest_completed` 信号回调中增加金币，并在 `_save_game()` 将 `quest_manager.save_progress()` 放进现有 `quests` 字段。当前奖励为完成时自动发放，不是待玩家点击领取的奖励。若要支持可领取奖励，必须重新设计领取状态和奖励原子性，不能复用或误解现有 `completed`。

### 2.2 HUD、面板与主城入口

`scripts/ui/hud.gd` 当前有英雄、装备、营地、背包、招募、地图、传送等按钮及其 pressed signals；没有红点节点、红点设置 API、每日奖励入口或日常活跃度按钮。任务文字通过 `set_quest_text()` 设置。

`scripts/core/town_building_registry.gd` 是主城建筑 ID、显示资料、投影位置及命中测试表。当前 4 个入口映射到已有的招募、营地、装备、背包面板；它不是业务状态管理器，也没有红点状态字段。`Main` 接收建筑点击并调用对应面板处理器。

`scripts/ui/recruit_panel.gd` 从 `RecruitmentManager` 渲染招募状态及碎片进度；碎片达到门槛时显示“合成解锁”按钮。是否有红点仍需确定是“存在未招募英雄”还是“现在即可合成”；建议仅对确实可执行的合成条件提示。

`scripts/ui/equip_panel.gd` 展示英雄套装和散件槽位；当前显示本身不等于有可领取/待处理动作。装备红点究竟表示可穿戴装备、空槽、可切换套装还是新获得装备，必须由产品定义；无定义前不应凭 UI 文本猜测。

`scripts/ui/backpack_panel.gd` 展示背包与邮箱。邮箱行有“领取到背包”操作；`Main._on_backpack_claim()` 在背包满时不领取，成功后刷新并保存。可作为现有可操作状态候选：邮箱非空且背包未满时可领取；邮箱非空但背包已满时不能显示同一种“可立即领取”提示。

### 2.3 存档

`scripts/core/save_manager.gd` 当前 `SCHEMA_VERSION = 1`，本地 `save.json` / `save_backup.json` 管理 JSON 字典及备份恢复。任务状态由 `Main` 放入 `quests` 字段，旧档缺少 `quests` 时 `QuestManager.load_progress({})` 初始化零进度。

当前没有 `daily_activity`、`daily_reset_key`、阶段奖励 claim 状态或红点状态字段。红点应由当前权威状态派生，不持久化红点布尔值。未来若要持久化每日进度，必须单独评审可选字段及旧档默认值；本设计不要求、不实施 schema 升级。

## 3. 建议架构（未来方案，不是已存在接口）

### 3.1 权威状态与组件边界

建议按职责划分，避免 UI/入口各存一份状态：

1. `DailyActivityManager`（待实现）：管理每日任务定义、每日任务进度、活跃度积分、阶段奖励状态、日期 rollover；通过纯查询接口提供快照/派生状态。奖励发放和领取必须有明确幂等契约。
2. 各已有业务 manager（任务、招募、装备、背包/邮箱、营地）继续拥有各自权威业务状态；不由红点层复制维护第二份业务状态。
3. `RedDotService`（建议名称，待设计确认）：以只读查询/适配器方式汇总各 manager 的状态，计算每个目标的 `visible`/原因/子项；不直接发奖励、不改任务或装备状态、不负责存档。
4. `Hud`、面板和主城建筑仅渲染 `RedDotService` 的结果。通用徽标组件可在 UI 层复用；建筑 ID 到红点 target ID 的静态映射可加入注册表，但业务判断留在 service/adapter。

推荐依赖方向：核心状态 manager → 红点派生服务 → HUD / Panel / TownBuildingRegistry 的显示 adapter。业务 manager 不依赖 UI；HUD 不扫描其他面板文字或自行推断业务规则。

### 3.2 候选接口与只读快照

以下仅为提案伪接口，命名、类型和回调频率需要实现前确认：

```gdscript
# DailyActivityManager proposed API (not implemented)
func load_state(saved: Variant, day_key: String) -> void
func record_event(event_id: String, occurrence_id: String, amount: int = 1) -> void
func claim_stage(stage_id: String) -> Dictionary
func get_snapshot() -> Dictionary
func save_state() -> Dictionary

# RedDotService proposed API (not implemented)
func refresh(sources: Dictionary) -> void
func is_visible(target_id: String) -> bool
func snapshot() -> Dictionary
signal state_changed(snapshot: Dictionary)
```

建议 `DailyActivityManager.get_snapshot()` 提供只读、版本明确的结构，例：

```text
{
  "day_key": "<由已确认时区/规则生成>",
  "tasks": {
    "<task_id>": {"progress": 0, "target": 1, "completed": false}
  },
  "activity_points": 0,
  "stages": {
    "<stage_id>": {"threshold": 0, "unlocked": false, "claimed": false}
  }
}
```

该示意不是现有存档形状；`unlocked` 可以从积分和门槛推导，不应重复保存。若只有“领取后”与“未领取”两种权威状态，应明确未解锁/可领取/已领取三态的来源。金额、任务和阶段门槛不得在 UI 中硬编码。

红点快照建议是 target ID 到 `visible` 及可选原因列表的派生结果，例如 `recruit`, `equipment`, `backpack`, `quest`, `daily_reward`, `town.recruit`；不把整份快照保存到用户存档。城市入口到子目标的映射必须明确且仅显示相应城市入口。

### 3.3 每日事件与积分规则待定

日常事件应由真实业务结果产生，而不是面板打开、按钮绘制或 UI 点击本身产生。候选来源（待产品/核心系统确认）：

- 指定目标击杀：在既有敌人死亡的成功结算路径发出带 `enemy_id` 的事件；Boss 和普通敌人需区分。
- 宝箱开启：仅在 `Chest.try_open()` 实际从未开转为已开并成功奖励时记录一次；重复交互不能重复增加。
- 装备处理/领取、招募、营地建设等：只有每日任务明确包含该行为时，才在核心操作成功后记录，不以 UI signal 发出作为完成依据。
- 登录/打开面板等是否计日常任务由产品确认；不得因本地离线启动/重复启动自动重复计数。

每个可计数的成功事件应有稳定的幂等键/唯一 occurrence ID，确保一次逻辑行为不会因重复 signal、重试、加载或重复输入计多次。需确认跨保存重启的防重复策略，特别是同一击杀/宝箱事件在状态落盘前退出的语义。

活跃度建议使用配置数据描述任务 `task_id`、事件类型、条件、目标数量、积分值及每日任务集合；阶段门槛和奖励 ID 也应配置化。积分规则需先决策：

- 任务仅在首次完成时加分，还是每次重复完成可继续加分；推荐“每日任务单次完成、加分一次”。
- 部分进度是否给积分；建议仅完成任务时授予积分，避免小数/逐次重入复杂度。
- 超出目标的事件是否封顶；建议进度 clamp 在 `[0,target]`，积分最多发一次。
- 同一事件可否完成多个不同任务；建议允许符合条件的多个任务各计一次，但单一任务只计一次。
- `QuestManager` 当前任务进度与每日任务是否共用事件/进度，不能假定共用；推荐每日状态独立，事件可由 Main/领域 manager 以 typed event 通知两者。

### 3.4 每日重置与时区

必须先由产品明确日界线时区、离线经过日期边界的处理、系统时钟回拨和跨时区策略。不得直接把设备本地日期当作永远可靠的权威时钟。

建议由可注入 `Clock/DayKeyProvider` 提供日期键，便于测试。每次启动及每次计入日常事件/领取阶段奖励前检查 day key：若已进入新日，先创建新日状态（任务进度、积分、阶段领取态重置），再处理当前事件。日期键相同不得重置；旧档缺日期键时采用一次性迁移默认策略，且不要误发旧周期奖励。实际持久化字段及兼容策略由单独实现 PR 确认。

时钟回拨不应静默产生同一天重复领奖；可考虑拒绝早于已记录 day key 的 rollover、保留较新周期状态或仅允许单调前进，具体规则需产品确认。没有可信在线时钟时无法彻底防止设备时钟篡改；本地单机项目需接受并记录该风险。

### 3.5 阶段奖励领取与一致性

阶段建议状态由积分门槛决定是否解锁，`claimed` 由权威 manager 状态决定；UI 仅显示锁定、可领取、已领取三态。

`claim_stage(stage_id)` 应验证：阶段存在、当前日可领取、未领取、奖励定义有效。扣发/领奖状态更新须做到单次原子逻辑：成功领奖后状态立即成为已领取并保存；重复请求返回“已领取/不可领取”且不重复发奖励。保存失败的恢复语义必须预先定下来，避免已加物品但 claim 标志没存、下次重复发放。既有 `SaveManager` 只提供整个字典保存与主/备份管理，没有事务/局部字段写接口，因此需评估完整加载-更新-保存路径，不能假设其有事务 API。

### 3.6 统一红点：数据源及语义候选

红点可按下列真实业务状态派生，但每个语义需产品确认：

| 入口 | 当前可观察状态 | 建议的候选“可处理”条件（待确认） | 不应采用的判断 |
|---|---|---|---|
| 英雄招募 | 招募状态、碎片数/需求；RecruitPanel 会展示“合成解锁” | 存在未招募且满足碎片/条件、点击可进入合成流程的英雄 | 仅有未招募英雄（可能被任务锁定） |
| 装备 | 套装、散件装备状态由 EquipmentManager 管理 | 存在需玩家决策的可穿戴新装备，且规则明确其目标英雄/槽位 | 无条件因存在任何装备或空槽亮红点 |
| 背包 | 背包、邮箱及背包容量；邮箱有领取操作 | 邮箱有可领取项且背包有空间；或其他明确待处理状态 | 背包非空本身（通常是常态） |
| 任务 | `counts`/`completed`；现有奖励自动发放 | 若强调未完成任务，只有明确的“当前可推进/待交付”状态可提示；若完成即自动结算则完成不应冒充可领奖 | 把 completed 直接当“可领取” |
| 每日奖励 | main 无每日任务、活跃度或领取状态 | 未来由每日状态提供 `claimable_stage_count > 0` 或符合已确认策略的未处理任务 | 未实现前显示/保存占位红点 |
| 主城建筑 | 四建筑静态映射招募/营地/装备/背包 | 每个建筑聚合映射面板对应 target；用同一派生快照 | 建筑 registry 自行复制业务条件、各面板各存 bool |

建议聚合规则：父入口红点 = 其子项红点逻辑 OR；若未来需要数量徽标，数量由各状态源的可行动项数聚合并定义去重规则。仅在 source 快照实际变化后刷新，并在启动初始化、对应状态成功变更/加载完成、��取成功后刷新。UI 打开可触发刷新校验但不得因此清除状态；只有权威业务操作完成后，状态源自然变更才消红点。每日 rollover 后重新计算每日任务/奖励入口及主城聚合。

任务红点语义必须明确。当前任务已完成即自动给金币，无需玩家领取，故不应显示“可领奖”红点。若设计目标是提示未完成任务，需任务系统明确哪些任务是玩家已接受、可推进或待交付；现有配置/管理器没有这些状态，不能直接把所有未完成任务标红。

## 4. 每日活跃度 UI 测试方案

这是未来功能完成后的验收用例清单，不代表当前可运行的每日活跃度测试；在核心数据/API 确认前不能写依赖假接口的自动化脚本。

### 4.1 面板和任务进度

1. 新玩家无日常状态时面板展示配置的每日任务列表、0/目标、0 积分及阶段锁定态；不显示虚假完成/领奖状态。
2. 每个任务核对名称、说明、进度、积分和可执行状态都来自配置/manager snapshot；列表滚动和空列表无错误。
3. 真实事件未发生时进度不变；条件事件达到阈值后进度达标、任务完成及积分只改变一次。
4. 错误敌人 ID、Boss 标记不符、无效/失败交互、重复 signal 均不计数；一个事件符合多个不同任务时各按规则更新，单任务不重复计数。
5. 进度不超过目标；部分进度、已完成任务、未解锁地图/不可达目标的呈现按已确认规则验证。

### 4.2 积分阶段和领奖

1. 积分低于门槛显示锁定；恰好达到门槛转换为可领取；超过多阶段门槛时各阶段状态正确。
2. 点击已解锁未领取奖励后，奖励按定义一次发放，claim 状态持久化，面板和入口红点同步消失。
3. 对同一 stage 连续快速点击、重复调用、保存后重启再领取均不得重复发放。
4. 锁定阶段、未知 stage ID、重复领奖、非法奖励定义、领奖保存失败均返回明确结果且无部分重复发放。
5. 领取一个阶段只清除对应阶段提示；其他可领取阶段仍显示；已全部领取时父入口红点消失。

### 4.3 每日重置、存档与兼容

1. 在同一日多次启动/打开面板不重置任务、积分或领奖状态。
2. 注入时钟跨日，下一次状态访问发生一次 rollover：日任务和积分重置、领取标记依规则重置、旧日状态不能产生新日重复奖励。
3. rollover 同时发生事件时，先新日初始化再计该事件；边界时刻（前一日最后瞬间、day key 翻转瞬间）结果确定。
4. 重启保存/恢复同日部分进度、已完成任务、已领取阶段后保持一致；旧存档无每日字段时给出安全默认且不崩溃、不自动发放奖励、不改变既有 `quests`/存档字段含义。
5. 时钟回拨、时区变更、离线跨日、存档损坏并从备份恢复、保存失败按已确认规则测试。
6. 存档 schema/可选字段变更只有在独立功能 PR 获准后才测试；本设计 PR 不添加这些字段。

### 4.4 红点和同步

1. 每个源从无状态变有待处理状态时，只显示映射入口和对应面板红点；非相关入口不亮。
2. 完成有效动作、领取奖励、招募成功、处理邮箱项后，派生状态更新且红点消失；失败/取消操作不应错误消红点。
3. 同一 target 同时有多个子项时，处理其中一个仍有其余事项则保持父红点；全部处理后父红点消失。
4. 打开/关闭面板、场景刷新、重复 refresh 不改变业务状态或发放奖励，不造成红点闪烁或重复信号。
5. main-town building 与 HUD 按钮映射同一个 target，刷新结果相同；切离主城时仅按约定隐藏建筑世界入口显示，不清除源状态；回到主城红点正确恢复。
6. 新建游戏、旧存档、备份恢复及每日 rollover 后重新计算红点；不从保存的 `red_dot=true` 恢复陈旧 UI 状态。
7. 使用隔离的 Godot `SceneTree`/Control 场景测试验证徽标显隐、信号更新与映射；真实分辨率、触屏遮挡和视觉层级仍需设备验收。当前 CI 以 headless 脚本为主，并没有成熟的截图/UI 自动化基架。

## 5. 建议的核心类、数据结构与文件清单

### 建议新建（未来功能 PR，不属于本设计 PR）

- `scripts/progression/daily_activity_manager.gd`：周期、任务进度、积分、阶段状态和幂等领奖。

- `tests/test_red_dot_service.gd`：派生规则、聚合和状态变更测试。
- UI 测试可独立 `tests/test_daily_activity_ui.gd`，待决定真实场景与可访问性标识后再建。

### 预计需要适配（不是本次修改）

- `scripts/core/main.gd`：构造并注入服务，桥接成功业务事件，保存/加载经批准的每日状态，操作成功后刷新红点。
- `scripts/ui/hud.gd` 及对应 `.tscn`：每日面板入口、可重用红点标记及 target 状态绑定。
- `scripts/core/town_building_registry.gd`、`scripts/core/map.gd`：只提供建筑 target 映射/绘制占位锚点；状态由红点服务注入，不在 Registry 保存业务红点字段。
- 招募、装备、背包、任务、营地 manager/UI：提供只读、明确语义的状态查询或领域事件；不各自私有维护重复红点变量。
- `.github/workflows/godot-cloud-validation.yml`：未来测试脚本和成功输出集成。
- `docs/CHANGELOG.md`、`docs/PROJECT_STATUS.md`：功能实现与存档兼容经验证后更新。

### 建议接口契约（必须待核心实现评审）

```text
DailyActivityManager:
  initialize(saved_optional_state, day_key, definitions)
  record_event(typed_event, occurrence_id)
  get_snapshot() -> read-only task/points/stage states
  claim_stage(stage_id) -> explicit success/failure result
  save_optional_state() -> optional serializable state

RedDotService:
  refresh(source_snapshots)
  is_visible(target_id) -> bool
  get_state(target_id) -> {visible, reasons/count?}
  state_changed(snapshot)
```

返回结构要稳定、可测试、不可由 UI 任意修改。奖励写入必须和 claim 状态更新有清楚的保存失败策略。上述接口均未存在于当前 main。

## 6. 需要核心系统/产品提供的接口与决策

1. 每日任务产品定义：任务列表、可重复性、目标、奖励、积分值和阶段门槛。
2. 可注入的日期/时钟服务、日界线与时区政策，以及回拨/时区变化/离线跨日语义。
3. 各领域成功事件来源及唯一 occurrence ID；特别是击杀、宝箱、招募、装备、营地操作的单次成功定义和持久化顺序。
4. 奖励库存服务/金币或物品奖励接口、原子领奖语义、保存失败和重复请求行为。
5. 任务状态产品语义：是否有“接受/待交付”阶段；当前任务完成自动给金币，不能提供可领奖状态。
6. 招募红点的条件：可合成 vs 任一未招募英雄；装备红点的 actionable 条件；背包/mailbox 空间条件；每日奖励红点是否按任务或阶段聚合。
7. HUD 按钮与主城建筑的 target ID、父子聚合规则、徽标数量/点样式及清除策略。
8. 是否新增可选 `daily_activity` 存档字段、默认值、备份恢复、旧档行为及版本迁移；由单独 PR 评审决定。本设计不改变 schema。
9. UI 自动化目标环境：Godot Control 场景 headless 验证覆盖范围，以及 Android 手动/截图验收矩阵。

## 7. 潜在风险

- **日界线与时钟操纵：** 本地单机没有可信服务端时间；跨时区、时钟回拨可能导致多领奖或丢进度。
- **事件重复/丢失：** 事件与存档写入非原子时，重启可重复计数/奖励或丢失一次进度；需要 occurrence ID 和持久化顺序设计。
- **奖励与 claim 状态不一致：** 先发奖后保存失败会重复；先标记已领后发奖失败会吞奖励。需定义原子策略/恢复方式。
- **数据源耦合/循环依赖：** 红点若读取 UI label 或让各 UI manager 互调，难以测试且容易产生逻辑循环；仅从核心状态的只读快照派生。
- **语义误报：** 将未完成任务、背包有物品、空装备槽或未招募英雄一概标红会产生永久噪声；只报告可执行且产品明确的动作。
- **父子重复计数：** 建筑、HUD、子面板同时为同一状态计数时徽标数膨胀；定义 unique target 与聚合去重。
- **旧存档兼容：** 新每日状态缺失必须给确定默认，不能因缺数据重置现有任务/资源，也不能自动补发历史奖励。
- **UI/设备差异：** Headless 逻辑测试无法验证触屏热区、竖屏布局、视觉遮挡和多分辨率显示。
- **无限进度与配置错误：** 日常目标、奖励引用及目标 ID 错配可能造成积分超发/永久不可领取；需配置校验和边界测试。

## 8. 实施顺序建议

1. 产品确认每日任务/领奖语义、时区、奖励与红点目标表。
2. 单独设计并评审可选存档字段兼容策略及事件幂等性；保持当前 schema 不动，直至批准。
3. 先实现纯逻辑 `DailyActivityManager` 与 `RedDotService`、时钟/奖励注入接口及单元测试。
4. 通过 Godot 4.7.2 CI 后，接入 Main 的领域成功事件与持久化。
5. 接入 HUD 与主城建筑/面板显示，测试状态同步及重复/失败动作。
6. 进行 Android 触控、每日跨日、存档恢复与可视化验收；各 PR 明确区分 headless 与设备结果。
